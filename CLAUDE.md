Google Cloud provider resources for the Pangea infrastructure DSL. All resource
code is **auto-generated** by `pangea-forge` via `iac-forge-cli`. Manual edits
to resource files will be overwritten on the next generation run.

## Structure

```
lib/
  pangea-gcp.rb                       # Entry point (generated -- requires all resources)
  pangea-gcp/version.rb               # Version constant (manual)
  pangea/

        core.rb                       # Provider-specific Dry::Types (generated)
      google.rb                       # Aggregator module (generated)

spec/

```

## Regeneration

Resources are generated by `pangea-forge` (the Pangea backend of `iac-forge`)
via `terraform-schema-importer`.

```sh
# 1. Fetch the provider schema:
#    mkdir /tmp/gcp && cd /tmp/gcp
#    printf 'terraform { required_providers { google = { source = "hashicorp/google" } } }\n' > main.tf
#    terraform init && terraform providers schema -json > schema.json
# 2. Regenerate (run from the pangea-gcp repo root):
terraform-schema-importer generate \
  --schema /tmp/gcp/schema.json \
  --provider "registry.terraform.io/hashicorp/google" \
  --provider-name google \
  --gem-name gcp \
  --output-dir .
```

**`--gem-name gcp` is load-bearing.** The gem ships as `pangea-gcp`, but the
resource prefix + module are `google` / `Pangea::Resources::Google`. Without
`--gem-name`, the importer emits `lib/pangea-google.rb` (not the `pangea-gcp.rb`
gem entry) — the require-index then points at bodies under the wrong gem name and
`require 'pangea-gcp'` fails. **This exact omission wedged the rio pangea-operator
with `uninitialized constant Pangea::Architectures` (2026-06-02): the require-index
was committed but the resource bodies under it were never emitted/committed.**
Always verify after a regen that `require 'pangea-gcp'` loads. (The importer's
`--verify` flag runs the host `ruby`; a stale system ruby false-negatives on the
Ruby-3.x vendored gems in `.gems/` — if so, verify with a ruby 3.3 directly.)
